# Bump: управление версиями проекта

`bump.bat` — автоматизированный BAT-скрипт для управления версиями Flutter-проекта, создания Git-коммитов и обновления журнала изменений (`changelog.md`).

Скрипт позволяет выполнять версионирование по принципам **Semantic Versioning (SemVer)**, автоматически увеличивать Flutter Build Number и при необходимости отправлять изменения в удалённый Git-репозиторий.

## 1. Требования

Для работы скрипта необходимы:

- Windows.
- Установленный Git.
- Установленный Windows PowerShell.
- Flutter-проект с файлом `pubspec.yaml`.
- Git-репозиторий с настроенным удалённым сервером (для использования `push`).

В корне проекта должны находиться:

```text
project/
├── bump.bat
├── bump.md
├── pubspec.yaml
├── version.txt
├── changelog.md
└── ...
```

`version.txt` и `changelog.md` создаются автоматически при необходимости.

## 2. Запуск

Общий синтаксис:

```bat
bump.bat "Текст коммита" <x|y|z> [push]
```

Параметры:

| Параметр | Обязательный | Описание |
|---|---|---|
| Текст коммита | Да | Описание изменений для Git-коммита и changelog |
| `x` | Да (тип версии) | Увеличение Major |
| `y` | Да (тип версии) | Увеличение Minor |
| `z` | Да (тип версии) | Увеличение Patch |
| `push` | Нет | Отправка созданных коммитов на удалённый сервер |

Примеры:

```bat
bump.bat "Исправлена ошибка авторизации" z
bump.bat "Добавлен новый функционал" y
bump.bat "Изменена архитектура приложения" x
bump.bat "Исправлена ошибка авторизации" z push
```

Сообщение коммита необходимо заключать в двойные кавычки.

## 3. Система версионирования

Используется классическая схема Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

| Компонент | Назначение |
|---|---|
| MAJOR | Несовместимые изменения |
| MINOR | Добавление функциональности с сохранением обратной совместимости |
| PATCH | Исправления ошибок и небольшие изменения |

### Типы обновления

**x — Major**

Увеличивает первую часть версии, остальные обнуляются.

```text
1.2.3 → 2.0.0
```

**y — Minor**

Увеличивает вторую часть версии, Patch обнуляется.

```text
1.2.3 → 1.3.0
```

**z — Patch**

Увеличивает последнюю часть версии.

```text
1.2.3 → 1.2.4
```

## 4. Хранение версии

Версия проекта хранится в двух файлах.

### version.txt

Содержит основную версию приложения без Build Number.

Пример:

```text
1.2.3
```

### pubspec.yaml

Содержит версию Flutter-приложения вместе с Build Number.

```yaml
version: 1.2.3+15
```

Формат:

```text
MAJOR.MINOR.PATCH+BUILD
```

При каждом запуске скрипта Build Number автоматически увеличивается на единицу независимо от типа обновления версии.

Пример:

```text
До:
version: 1.2.3+15

После выполнения bump.bat "Исправление" z:
version: 1.2.4+16
```

### Приоритет определения версии

1. Если `version.txt` существует, версия считывается из него.
2. Если `version.txt` отсутствует, начальная версия берётся из `pubspec.yaml`.
3. Если версия в существующем `version.txt` имеет некорректный формат, выполнение прекращается с ошибкой.
4. Если в `pubspec.yaml` отсутствует корректная версия, выполнение прекращается с ошибкой.

## 5. Алгоритм работы

Скрипт выполняет операции последовательно.

| Этап | Операция | Описание |
|---|---|---|
| 1 | Проверка параметров | Проверка аргументов командной строки |
| 2 | Проверка Git | Проверка наличия Git-репозитория |
| 3 | `git add -A` | Добавление всех изменений рабочего каталога |
| 4 | Первый коммит | Создание коммита с пользовательским сообщением |
| 5 | Получение SHA | Получение короткого идентификатора первого коммита |
| 6 | Обновление версии | Изменение `version.txt` и `pubspec.yaml` |
| 7 | Обновление changelog | Добавление записи в начало `changelog.md` |
| 8 | Второй коммит | Создание коммита с обновлением версии |
| 9 | Git Push | Отправка изменений на сервер при наличии параметра `push` |

### Особенности коммитов

На одно обновление версии создаются два коммита.

**Первый коммит** содержит изменения приложения и пользовательское сообщение.

**Второй коммит** содержит только служебные изменения:

- `version.txt`;
- `pubspec.yaml`;
- `changelog.md`.

Такой подход позволяет сохранить действительный SHA первого коммита в changelog.

## 6. Changelog

Файл `changelog.md` содержит историю изменений проекта.

Каждый запуск скрипта добавляет новую запись в начало файла.

Формат записи:

```markdown
## [1.3.0] - 2026-11-04 (a1b2c3d)
* Добавлена интеграция с новым API

```

Поля:

| Поле | Описание |
|---|---|
| Версия | Новая версия приложения |
| Дата | Дата выполнения обновления |
| SHA | Короткий SHA первоначального коммита |
| Описание | Текст пользовательского коммита |

Старые записи сохраняются без изменений.

## 7. Отправка на сервер

Если при запуске указан параметр `push`, после создания обоих коммитов выполняется:

```bash
git push
```

Пример:

```bat
bump.bat "Добавлен новый модуль" y push
```

Если параметр `push` не указан, изменения остаются только в локальном репозитории.

## 8. Обработка ошибок

Скрипт проверяет результаты основных операций.

Возможные причины остановки:

- Текущая директория не является Git-репозиторием.
- Не удалось добавить файлы в Git.
- Не удалось создать первоначальный коммит.
- Не удалось получить SHA коммита.
- Не найден `pubspec.yaml`.
- Некорректный формат версии.
- Не удалось обновить файлы версии или changelog.
- Не удалось создать второй коммит.
- Не удалось выполнить `git push`.

При ошибке выполнения скрипт возвращает код завершения `1`.

При успешном выполнении возвращает `0`.

**Важно:** скрипт не выполняет автоматический откат уже созданных коммитов. Если ошибка возникла после первого коммита, он останется в локальной истории. Если второй коммит не удалось создать, служебные изменения могут остаться в рабочем каталоге.

## 9. Рекомендации

1. Запускайте `bump.bat` из корневой директории проекта.
2. Перед запуском убедитесь, что все изменения, которые должны попасть в коммит, находятся в рабочем каталоге.
3. Не изменяйте версию вручную одновременно в `version.txt` и `pubspec.yaml`.
4. Используйте `x` только для несовместимых изменений.
5. Используйте `y` для добавления новой функциональности.
6. Используйте `z` для исправлений и небольших изменений.
7. Перед первым использованием проверьте работу скрипта на отдельной Git-ветке.
8. Не используйте `push`, пока не убедитесь, что оба локальных коммита созданы успешно.
